- **Windows.** An AppContainer plus a Job Object. Scripts and solves run in a normal AppContainer. The stricter one (LPAC) is not used, because Python cannot start or import aicad in it without granting more. A normal AppContainer can still read files Windows has opened to every AppContainer, mostly under `C:\Windows`. User files outside the project are blocked either way. The drawing-font list is built once in the Python install, which the container can read. Matplotlib and other library caches, which would otherwise sit in the user profile, are kept in `.aicad/cache` inside the project. The profile itself is not redirected. After the script exits, aicad grants the current user access to files the container created, so the result can be read. The job caps memory, CPU time, and how many processes the script can start, and it does not let a child leave the job. User time at the CPU cap stops the script, including when the exit does not name a signal. The job is terminated when the tool returns, so a child the script started does not keep running. `os.kill` of another process is refused in the script. A job cannot stop the script from calling the Windows `OpenProcess` function on a process outside the job. An AppContainer can open a process only when that process grants the container. This aicad process does not, so `OpenProcess` and `TerminateProcess` on aicad fail. aicad does not rewrite that access list, because doing so stopped later scripts from finishing. Another program can still be opened when it already allows every AppContainer. That is a gap. A traverse grant that does not finish does not change that folder after the wait ends. aicad has to mark the Python install so the container may read it. That works for the usual per-user install from python.org. If Windows refuses that change, the script does not run. An administrator approves `aicad sandbox-setup` once per computer. It adds permanent firewall rules and filters that block one fixed container's inbound and outbound traffic for every protocol, with no port limit. No run installs or removes anything, and a normal account cannot remove the block. A network-off script runs in that container, and only when the filters can be read and a TCP connection and both a connected and an unconnected UDP send are refused. A successful send is not a refusal, and a timeout is not a refusal. A helper program such as the solver gets the same check first, in the same container. Until setup has run, no script or helper starts. Turning the network on runs the script in a second container the block does not name, so the block stays in place. That container still does not by itself reach localhost; Windows requires a separate loopback exemption for that.
