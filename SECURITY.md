# Security

Report a vulnerability in private. Please do not open a public GitHub issue for a problem that is not fixed yet.

## How to report

Use GitHub private vulnerability reporting on this repository:

https://github.com/TheRealBillyB/ai-first-cad/security/advisories/new

That form stays off the public issue list. Turn on private vulnerability reporting in the repository settings. Until the form is available, send a private message on GitHub to [TheRealBillyB](https://github.com/TheRealBillyB).

Include what you can:

- What you found, and what an attacker could do with it.
- The version, the commit, and the operating system.
- The steps to reproduce it, including a design file or a script if one is required.
- Whether you have already seen it used against someone.

You will get an acknowledgement. Please give the maintainer time to publish a fix before you write about the problem in public.

## What is in scope

The local tool: the MCP server, the workspace app, the command line, and the Python API. A script the assistant runs, a plugin, and a design file from someone else are in scope. So is anything in a downloaded project that runs code, reads files outside the project, or reaches the network when the person did not ask it to.

## What this version does

A script the assistant sends runs in a separate process. That process can read and write the project folder. It cannot use the network unless you turn that on yourself (`aicad app --script-network`, or **Allow network on the next script** in the app). It stops if it runs too long or uses too much memory. If this computer cannot apply those limits, the script is not run.

- **Linux.** Landlock limits files and blocks TCP. When the kernel can scope signals, Landlock also blocks a signal to any process outside the script. The Landlock version is the one this kernel reports. A project file, a configuration file, an environment variable, a plugin, or a tool argument cannot ask for an older one. A symlink, named pipe, socket node, or device node cannot be created outside the project. A small filter blocks every other kind of socket, including UDP, and blocks starting a new session. The same filter refuses a signal call unless it names the script process that installed it, and it refuses a signal sent through a pid file descriptor. It also refuses a resource limit aimed at another process, and a file-owner or terminal notice that can deliver a signal. A limit on this process still works. A child the script forks inherits that filter, so it can signal that script process, which is inside the sandbox, and no other pid. That holds on the kernels that already run a script, including those whose Landlock cannot scope signals yet. It accepts only the native instruction set, so a 32-bit call cannot open a socket the filter already refused. It also refuses io_uring, ptrace, cross-process memory, and taking a file from another process. CPU and memory use `setrlimit`. The process cap counts only the script's own threads. When this user can create a cgroup without root, the cap is `pids.max` on a cgroup made for that script. If the script cannot be moved into that cgroup, it is not run. Otherwise the parent counts the threads in the script's process tree and stops the group above the same number (256). The user-wide process limit is not used, because it also counts other programs and was stopping geometry when a browser was already open. A classic seccomp filter cannot count `clone` or `fork`, so it does not limit how fast those calls happen. The process filter is installed on every thread that already exists. If another thread is already there, the script is not run. The script process adopts children that lose their parent. When the tool returns, the script's process group is killed, so a child it started does not keep running. `/proc` stays readable so Python can start. Another process's command line under `/proc` can still be read. Its environment and open files cannot.
- **Mac.** `sandbox-exec` applies a Seatbelt profile, and `setrlimit` sets CPU time. Apple has deprecated `sandbox-exec`. It is still the practical profile that does not need a container. The address-space cap is not applied. macOS maps a system library cache larger than 4 GiB into every process, and setting the cap stops the script before it runs. The parent instead checks the script's resident memory about four times a second and stops the whole process group when that passes 4 GiB. The wall clock still stops a script that runs too long. The profile allows Mach service lookup so Python can start. That is a gap: a system service could do something the script is not allowed to do itself. It also allows reading the `/` directory itself. Without that, the process aborts instead of starting. Files in other directories stay closed. `os.kill` of another process is refused in the script. A child that leaves the script's process group is killed, and the group is killed when the tool returns.
- **Windows.** An AppContainer plus a Job Object. The stricter container is used when Python can still start that way. A normal AppContainer can still read files Windows has opened to every AppContainer, mostly under `C:\Windows`. User files outside the project are blocked either way. The drawing-font list is built once in the Python install, which the container can read. Matplotlib and other library caches, which would otherwise sit in the user profile, are kept in `.aicad/cache` inside the project. The profile itself is not redirected. After the script exits, aicad grants the current user access to files the container created, so the result can be read. The job caps memory, CPU time, and how many processes the script can start, and it does not let a child leave the job. User time at the CPU cap stops the script, including when the exit does not name a signal. The job is terminated when the tool returns, so a child the script started does not keep running. `os.kill` of another process is refused in the script. A job cannot stop the script from calling the Windows `OpenProcess` function on a process outside the job. An AppContainer can open a process only when that process grants the container. This aicad process does not, so `OpenProcess` and `TerminateProcess` on aicad fail. aicad does not rewrite that access list, because doing so stopped later scripts from finishing. Another program can still be opened when it already allows every AppContainer. That is a gap. aicad has to mark the Python install so the container may read it. That works for the usual per-user install from python.org. If Windows refuses that change, the script does not run. When the network is off, firewall rules and a filter block that container's inbound and outbound traffic for every protocol, with no port limit. The script runs only after a TCP connection and both a connected and an unconnected UDP send are refused. A successful send is not a refusal, and a timeout is not a refusal. Turning the network on removes the block. It still does not by itself allow localhost; Windows requires a separate loopback exemption for that.

A design script, one program that calls several steps, stays off until you allow it with `aicad allow-scripts` or the button in the app. The app shows a warning before you do. Each of those runs is appended to `.aicad/script_log.jsonl` in the project. That log sits in the project folder, so a later script can edit it. It is a record you can read, not a lock. A script that only builds one solid (`part = ...`) uses the same confined process. It does not need the allow step. A design script can call only the public document methods. The check report lists only those calls, and only when the script made them. The process that ran the calls writes that report. A result written by the script is not the report. Earlier calls stay in the report.

A shared STEP file larger than 64 MiB is not read, and a project file served to the workspace stops at 32 MiB. A mesh stops at one million triangles. A script's file-size cap stays at 512 MiB, and a setting cannot raise it. Opening a project does not run Python stored in it. A script part shows its text and, when you have built it before, the solid from that build. STEP files, operation lists, and sketches are data. Importing a STEP file reads that file and does not open another path named inside it. A STEP file in the project that has another name is not opened. A script result that is a link is not read. A geometry file or a picture named by that result is opened only when it is a regular file inside the project. A font configuration file shipped in the project is not read when the geometry libraries are imported. Those libraries use a configuration file packaged with aicad. The process working directory is not changed. An entry title and rationale are one line, with no line break and no comment, so a generated master stays one section.

A reserved device name such as NUL, CON, PRN, AUX, COM1 through COM9, or LPT1 through LPT9 is refused as an output file or folder name, including a superscript digit. On the command line, an absolute export path is the location the person named. A drawing, bill of materials, or exploded view from the workspace stays inside the project. A bill of materials keeps a route name and a material as text. A strength-check picture from a position-error budget stays inside the project.

A URDF or MJCF export escapes a part or joint name. A quote in that name stays inside its attribute, and the file parses as one document. The mesh folder is created in that export folder. A mesh folder that is a link is not followed.

ffmpeg, CalculiX, and a slicer are started from PATH outside the project. A copy in the project is not started, and the current directory is not searched.

The sandbox process uses the project folder as its working directory. That folder is not placed on Python's import path. The child does not inherit the parent's PYTHONPATH. It receives only this install's import roots. A module or package shipped in the project cannot run in place of the sandbox. The same rule applies when the project is built again. The limits are applied before the script runs. A child does not inherit loader variables, interpreter startup variables, or the parent's PATH. CalculiX, ffmpeg, and a slicer are started with that same environment.

Files in the project, including `.aicad` and `.env`, do not turn the network on or raise those limits. A link that points outside the project is not written. A session, a note, a requirements file, a blueprint, and a STEP file are read from the project directory without following a link. A session larger than 32 MiB, or nested more than 48 levels, is not read. A STEP file larger than 64 MiB is not read. If a file in the project has more than one name, the script is not run, because writing that file would change every name. The script log is not read when that file has another name. A plan file is not opened when it is a link or has another name, and a plan folder that is a link is not listed.

Plugins are separate. Installed packs are listed from entry points without importing them. A third-party pack runs only after you allow the publisher, the version, and the permissions it declared. A pack ships with aicad only when its metadata directory is the one next to this copy. The package name is not used for that, so another package with the same name still needs an allow. An entry-point file that cannot be read skips that package and lists a warning; the other packages are still listed. Opening a design does not allow or load a plugin. A design script cannot allow or load a plugin either. That refusal is a flag in the running script process, not an environment variable the script can clear. The consent path it reports is the home config, not a cache folder inside the project. The warning is written by aicad, and the permission list is a declaration, not a sandbox. A plugin export is written inside the project. A path outside that folder is refused. See [docs/plugins.md](docs/plugins.md).

A one-shot network grant is used up only when the design script finishes without an error. If the script fails, the next run still has the grant.

## Security tests

These checks use a marker file outside the project. A project file is data. The tests do not run it as a program.

- **R.** Text in a note, a part name, a blueprint, or a session does not start a script, open a socket, or write outside the project. A design script stays off until it is allowed.
- **S.** The workspace server rejects a foreign host and a foreign origin. A command with no origin is refused. Responses do not offer cross-origin access. A WebSocket upgrade is not accepted. The session token is not written to the server log.
- **T.** A setting cannot raise a script's time or memory cap. A blueprint past 20 MB is not opened. A PNG header with a huge dimension is not opened. A zip or 3MF in the project is not extracted on open. A script past the character cap is not run.
- **U.** A session, a note, a requirements file, or a blueprint that is a link to a file outside the project is not read.
- **V.** A STEP, STL, URDF, or MJCF export, and a session record, do not contain an environment value, a token, or the account name unless that text is part of the model.
- **W.** Opening a project and exporting a part do not run git, a hook, a filter, or `core.fsmonitor`.
- **X.** A project `.env`, pip or uv configuration, `pyproject.toml`, or `requirements.txt` does not change the process environment. A module in the project does not replace the standard library, and `sitecustomize` there does not run.
- **Y.** A parent loader, startup, or import-path variable does not reach a script or CalculiX.

Master documents are generated from the entry files in the repository. A symlink or junction on that path is not followed, and a file with another name is not read or written. Generating the masters does not run an entry as code.

This sandbox is for one person on their own machine. It is not a boundary between tenants. The choices are recorded in [docs/DECISIONS.md](docs/DECISIONS.md).

The workspace app listens on this computer only. A bind address that is not loopback is refused. It answers `localhost` and `127.0.0.1` on the port it opened, and it refuses a connection whose peer is not loopback, and a request whose `Origin` is some other site. Responses refuse to be framed, and they ask the browser not to send the address of a request onward. A picture response, whose address carries the session, is not stored. A command that does not name this app as its origin is refused too. A read from the page often sends no origin; that read still needs the session token. Each launch picks a new session token, puts that token in the page it serves, and accepts an API call only when the page sends the token back. The picture requests are the one exception: an image tag cannot set a header, so those carry the same token in the query. Names, notes, and other text from the project are shown as text. The workspace file view does not open a file that is a link or that has another name. A call from the page is the person. A call from the attached assistant is the assistant. The command body cannot choose which of those it is. Allowing design scripts, granting the network for one script, saving settings, and starting a chat require the page token. The assistant token cannot do those.

That stops another website, including one that tries to reach this computer by a DNS name that merely points here. It does not stop a program that already has a shell on this computer. An AI with that access can read the page, copy the session, and do what you can do. If a later approval step treats a click in the app as already approved, that step is a guardrail for an assistant that follows the rules. It is not a security boundary against a malicious program on this computer.
